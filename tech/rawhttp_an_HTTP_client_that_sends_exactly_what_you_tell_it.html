rawhttp: an HTTP client that sends exactly what you tell it

Tue, Sep 22.2026

A low-level, memory-safe raw-socket HTTP client in C, built for request-smuggling research. No libcurl. No normalization. It puts exactly the bytes you asked for on the wire — even the illegal ones — and that turns out to be the whole point.

Why build another HTTP client



There are a thousand HTTP clients and every one of them is trying to help you. That is precisely the problem.

curl, requests, every browser stack, every proxy library — they all "clean up" your request on the way out. Send two Content-Length headers and they pick one for you. Mix Content-Length with Transfer-Encoding: chunked and they resolve the ambiguity silently. Fix your casing. Reorder your headers. Add the ones you forgot. For 99% of the world that is a feature. For anyone studying HTTP request smuggling it is a lobotomy, because smuggling is the study of ambiguity — the exact bytes a "helpful" library deletes before you ever see them hit the socket.

So I wrote rawhttp: a client whose defining trait is that it does not help. When you hand it a request, it writes those bytes. All of them. In order. Wrong Content-Length and all. It is a scalpel, and like a scalpel it assumes you know where you are pointing it.

The interesting part isn't the CLI. It's what you have to build underneath to earn the right to say "I send exactly these bytes" and mean it — your own socket layer, your own transport abstraction, your own HTTP response parser, your own chunked decoder, and enough discipline in the memory model that a fuzzer throwing garbage at your parser doesn't hand an attacker your process. In C. Which is either the perfect language for this or a cry for help, depending on the hour.

The shape of the thing



rawhttp is a small library (librawhttp.a) with a thin CLI bolted on top. Everything except main.c compiles into the library, which is what lets the tests and fuzz harnesses link the real code instead of a copy of it.

It layers like this, base at the bottom:

┌───────────────────────────┐
│  CLI  (main.c)            │
│  args · dispatch · render │
└─────────────┬─────────────┘
              │
┌─────────────▼─────────────┐
│  modes                    │
│  client · raw · smuggle   │
│  fuzz · scan              │
└─────────────┬─────────────┘
              │
┌─────────────▼─────────────┐
│  protocol                 │
│  request · response       │
│  chunked · output         │
└─────────────┬─────────────┘
              │
┌─────────────▼─────────────┐
│  transport                │
│  io · transport · socket  │
└─────────────┬─────────────┘
              │
┌─────────────▼─────────────┐
│  base                     │
│  error (rh_err) · buf     │
└───────────────────────────┘

Each layer only knows about the one below it. The parsers never touch a file descriptor. The socket layer never knows what HTTP is. That separation is what makes the whole thing testable — and it is the reason a fake in-memory "transport" can feed the parser fuzzer input without a single syscall.

The base layer: errors and bytes



Two decisions at the bottom shape everything above them.

One error vocabulary. Every function that can fail returns an rh_err — a plain enum — instead of the C zoo of -1, errno, NULL, and "check the out-param". RH_OK is zero, and the rest name a category: RH_ERR_DNS, RH_ERR_CONNECT, RH_ERR_TLS, RH_ERR_PARSE, RH_ERR_IO, RH_ERR_MEM, RH_ERR_INVAL, RH_ERR_TIMEOUT, RH_ERR_LIMIT. The last two matter: they carve out "well-formed but I refused it" from "the I/O genuinely broke", which is a distinction you desperately want when a response is 512MB of adversarial garbage.

Bytes, not strings. The core buffer, rh_buf, tracks a length and a capacity and never assumes a trailing NUL:

typedef struct {
    char  *data;
    size_t len;   /* bytes held      */
    size_t cap;   /* bytes allocated */
} rh_buf;

This looks trivial. It is load-bearing. HTTP bodies contain NUL bytes. Smuggling payloads contain NUL bytes. The moment you reach for strlen you have introduced a truncation bug that an attacker controls. So rh_buf is length-first everywhere, growth is doubling with an overflow check (a real one — len + need is tested for wraparound before it is trusted), and when the program finally dumps a response to stdout it uses write(), not printf, so a NUL in the body doesn't cut the output in half.

The transport vtable: the trick that pays for itself



Here's the piece I'm quietly proud of. HTTP-over-TCP and HTTP-over-TLS are the same protocol reading through two very different pipes. Most code handles this with an if (is_tls) smeared through every read and write. That is how you get eleven subtly different bugs.

Instead, rh_transport is a vtable — a struct of function pointers:

struct rh_transport {
    void *ctx;   /* fd wrapper, or SSL/SSL_CTX pair */
    rh_err (*read )(rh_transport*, void*, size_t, size_t*);
    rh_err (*write)(rh_transport*, const void*, size_t, size_t*);
    void   (*close)(rh_transport*);
    int    (*get_fd)(rh_transport*);
    struct timespec first_byte_at;
    int    first_byte_recorded;
};

There are two backends. The plain one wraps a socket fd. The TLS one wraps an OpenSSL SSL object. Both fill in the same four function pointers, and everything above them — the send loop, the response parser, the chunked decoder — only ever calls t->read and t->write. They do not know or care which pipe is underneath.

   parser / io.c
        │  t->read()
        ▼
  ┌───────────────┐
  │  rh_transport │  (vtable)
  └──┬─────────┬──┘
     │         │
  ┌──▼──┐   ┌──▼───┐
  │ TCP │   │ TLS  │
  │recv │   │SSL_  │
  │send │   │read  │
  └─────┘   └──────┘

The payoff shows up in three places at once. TTFB timing is recorded in one spot — the first read that returns bytes stamps first_byte_at — and it works identically for TCP and TLS because both call the same helper. And when I needed to fuzz the parser, I wrote a third backend in about twenty lines: a transport whose read() hands back slices of a fixed buffer. The parser couldn't tell it wasn't a socket. That is the entire value of an abstraction — it's not elegance for its own sake, it's the ability to swap the bottom of the stack without the top noticing.

One honest caveat lives right in the code: get_fd() exists so the idle-timeout logic can poll(), and for TLS a readable fd doesn't guarantee a full decrypted record is ready. For "has anything arrived" idle detection that's good enough. For a strict parser it would be a bug. Knowing which is which is most of the job.

Data flow: the life of one request



Normal mode — a real HTTP/1.1 client — is the reference path. Everything else is a variation on it. The whole trip lives in one function, rh_client_request():

   URL string
      │  url.c: parse
      ▼
   rh_url {scheme,host,port,path}
      │  socket.c: connect (+timeout/proxy)
      ▼
   fd ── transport.c ──► rh_transport
      │  request.c: build bytes
      ▼
   rh_buf request
      │  io.c: rh_send_all()
      ▼
   ═══ the wire ═══
      │  response.c: read headers
      ▼
   status line + headers parsed
      │  pick body framing:
      │  chunked > Content-Length > close
      ▼
   rh_response {status, headers[], body}
      │  main.c: render (raw/pretty/json)
      ▼
   stdout

A few things worth slowing down on.

Building the request is where "unhelpful" becomes concrete. rh_request_build() adds Host, Connection: close, User-Agent, and a Content-Length — but only when you didn't supply them. Give it your own Content-Length header and it will not touch it, will not correct it, will not warn. Give it two and it emits two. That single design choice — "the caller is trusted completely" — is the difference between an HTTP client and a smuggling tool.

Reading the response is careful about the network being a byte stream, not a message stream. rh_response_read_headers() loops on rh_recv_some() — one read at a time — appending to a buffer and scanning for the \r\n\r\n that ends the header block. It never assumes one recv() returned the whole thing, because TCP makes no such promise. Once the headers are in, body framing follows the same precedence a real client uses: Transfer-Encoding: chunked wins, else Content-Length, else read until the peer closes.

The parser is strict on purpose. A header line with whitespace before the colon — Foo : bar — is rejected, not tolerated. RFC 7230 forbids it precisely because parsers disagree on it, and disagreement between a front-end and a back-end is the raw material of an exploit. A "nice" parser papers over it. This one refuses, because refusing is the security-correct behavior and because a tool built to study parser disagreement has no business introducing its own.

The five modes



The modes are mutually exclusive and every one of them runs through the same transport and I/O plumbing. What changes is where the bytes come from and how much interpretation happens on the way back.

        rawhttp
           │
   ┌───────┼───────┬───────┐
   ▼       ▼       ▼       ▼
 normal   raw   smuggle  fuzz
   │       │       │       │
   │       └───┬───┘       │
   ▼           ▼           ▼
 client   raw.c send   fuzz.c
 request  verbatim     corpus
                           │
                     ┌─────┴────┐
                     ▼          ▼
                   scan (pool of normal)

Normal mode is the client above: parse a URL, build a real request, frame the response properly. Use it when you want an actual HTTP client that happens to verify TLS by default and never lies to you about what came back.

Raw mode (--raw FILE --target host:port) is the honest heart of the tool. It reads a file, writes those exact bytes, and dumps whatever comes back — no request building, no response parsing, none. It prints a hex dump of the payload before sending so you can verify every byte, then reads until the peer closes or goes quiet for two seconds. --raw2 sends a second payload on the same connection, which is real pipelining, not a reconnect. This is how you send a request that no request-builder would ever agree to construct.

Smuggle mode (--smuggle cl.te|te.cl|cl.cl) generates the three classic desync payloads and sends them through the raw path. It's a convenience layer over raw mode — the payload builders live in smuggle.c, and the interesting detail is that they refuse to invent a mismatch for you. CL.CL emits two Content-Length headers with the same value by default; the attack only happens once you override one with --cl1/--cl2 to disagree. The tool won't guess your exploit. --probe fires a plain follow-up request on the same connection afterward — a wrong-looking answer to the probe is what actually proves the desync, because the smuggling request's own response usually looks perfectly normal.

Fuzz mode (--fuzz FILE --marker STR) takes a request template with a marker, substitutes each payload from a built-in twelve-entry corpus (empty, long strings, CRLF injection, NUL bytes, control characters, path traversal, format strings, and friends), sends each, and diffs the result against a baseline on three axes: status code, response length, and TTFB. It flags anything that deviates and prints the raw numbers regardless, because the thresholds are there to catch your eye, not to make the decision for you.

Scan mode (--scan-file FILE --concurrency N) is the only concurrent one. It reads a list of URLs and fires them through a pthread worker pool, each worker running the exact same rh_client_request() normal mode uses. Which brings me to the decision I like most.

The design decision I'd defend in a bar fight



Timeouts and proxying are global.

--timeout and --proxy don't get threaded as parameters through every mode's call chain. They live as file-scope config in socket.c, set once from the CLI before anything connects, and read inside rh_tcp_connect(). Every mode inherits them for free — normal, raw, smuggle, fuzz, and scan all route through that one connect function.

"Global state, in a concurrent program? Bold." Here's why it's fine: the config is write-once, read-many. The CLI sets it before a single thread spawns, and after that it is immutable. Immutable shared state needs no lock. The scan workers hammer rh_tcp_connect() from eight threads and never contend, because there is nothing to contend over. The alternative — a timeout and proxy parameter on rh_raw_send_and_dump, rh_raw_send_sequence, rh_client_request, and every builder that calls them — is more "correct" by dogma and strictly worse to live in. I traded a purity point for a real reduction in call-site noise, and I'd make the trade again.

The other half of that story is client.c. Normal mode and scan mode both call rh_client_request(). Not "similar code" — the same function. Which means their connect, build, and framing behavior physically cannot drift apart. A scan worker is just that function plus a mutex-guarded index into the URL list. The mutex guards exactly one thing — which URL is next — and the results array is written per-index with no sharing, so the only synchronization in the whole scanner is a couple of instructions.

Timeouts, without going non-blocking everywhere



The timeout implementation is a small case study in doing the least work that's actually correct.

Connect timeouts genuinely need non-blocking I/O: you set the socket non-blocking, call connect(), get EINPROGRESS, poll() for writability with your deadline, then check SO_ERROR. There's no shortcut — a blocking connect() to a black-holed host hangs for the OS default, which is about two minutes of your life you won't get back.

But read and write timeouts don't need the whole event-loop circus. SO_RCVTIMEO and SO_SNDTIMEO — socket options — make recv() and send() return with EAGAIN after the deadline. And because TLS sits on that same fd, those options bound SSL_read too, for free. So the transport layer maps EAGAIN/EWOULDBLOCK to RH_ERR_TIMEOUT and the whole stack above it gets timeouts without ever learning what non-blocking sockets are. The connect path pays the complexity cost because it has to; nothing else does.

The Makefile is the development workflow



The build isn't an afterthought here — it encodes how you're meant to work on the project.

make          release  -O2
make debug    ASan + UBSan
make test     build+run unit suite
make fuzz     libFuzzer targets (clang)
make fuzz-replay  corpus replay (gcc)
make clean

Everything compiles under -std=c11 -Wall -Wextra -Werror. The -Werror is not machismo; in C the warnings you ignore are the bugs you ship. A signed/unsigned comparison, an unused result, an implicit declaration — these are exactly the mistakes that turn into memory corruption three functions later, and the compiler will tell you about them for free if you let a warning fail the build.

librawhttp.a is built from every source except main.c, which is the small structural decision that makes testing possible: the test binaries and fuzz harnesses link the library, so they exercise the real code paths rather than a well-meaning reimplementation. The debug target swaps -O2 for -O0 -g and adds the sanitizers; test compiles each tests/*.c into its own binary against the sanitized library and runs them; fuzz reaches for clang because libFuzzer is a clang thing, while fuzz-replay builds the same harnesses with a standalone driver under gcc so you can replay a corpus — or a crash — without clang installed. That last split matters in CI, where you want the corpus smoke-test to run even on a box that only has gcc.

Sanitizers, and why C without them is negligence



Writing a network parser in C means writing code that reads attacker-controlled bytes into buffers you manage by hand. The failure modes aren't "wrong output" — they're "attacker owns your process". You do not get to hand-wave that. You instrument for it.

AddressSanitizer catches spatial and temporal memory bugs: reads and writes past the end of a buffer, use-after-free, double-free, and leaks. It works by shadowing memory — every allocation gets poisoned red-zones around it, and every load/store is checked against that shadow map at runtime. When your chunked decoder computes an offset wrong and reads one byte past a chunk, ASan stops the program at the instruction that did it and prints the allocation it belonged to. Without it, that same bug is a heisenbug that shows up as garbage output on a Tuesday.

UndefinedBehaviorSanitizer catches the things C says are your problem: signed integer overflow, shifts past the width of a type, misaligned pointers, dereferencing NULL. This codebase is full of arithmetic on lengths and offsets — data_start + chunk_size + 2, hex parsing accumulating into a size_t, the rh_buf growth math. Every one of those is a place an overflow could quietly wrap and turn a bounds check into a bypass. UBSan makes the wrap loud.

They're wired straight into the workflow: make debug and make test both build with -fsanitize=address,undefined, so the tests don't just check behavior — they run the whole suite under instrumentation that turns latent corruption into a hard failure with a stack trace. That's the difference between "the tests pass" and "the tests pass and nothing touched memory it shouldn't."

Testing and fuzzing: pointing the tool at itself



The unit suite lives in tests/, one binary per file, each linking librawhttp.a and running under ASan/UBSan via make test. They cover the pieces where correctness is exact: target parsing, the smuggling payload builders (byte-for-byte against known-good reference payloads — more on that in a second), raw-mode send sequencing, transport round-trips including that TLS verification rejects a self-signed cert.

That byte-for-byte smuggle test earned its keep. An early version of the TE.CL builder emitted a NUL byte (0x00) where the terminating chunk's ASCII 0 (0x30) should have been. The payload looked right in a casual glance and was completely inert on the wire — the back-end never saw a valid end-chunk, so the desync silently never fired. A test that asserts the exact bytes catches that instantly. A test that asserts "it built something" sails right past it. When the output is a wire protocol, "looks right" is a lie; assert the bytes.

Then there's the fuzzer. The response parser and chunked decoder are the two components that eat untrusted input, so they get libFuzzer harnesses in tests/fuzz/. Each harness spins up that in-memory transport I mentioned — the third vtable backend — hands the fuzzer's bytes to the parser through it, and lets libFuzzer + ASan + UBSan go feral. The corpus is seeded with valid and deliberately-broken responses. I also threw a couple hundred random and malformed inputs at the replay build; nothing tripped a sanitizer, which is the outcome you want but never assume. A parser that survives a fuzzer isn't proven correct — it's just proven not-trivially-ownable, which for code that reads hostile bytes is the floor, not the ceiling.

Debugging low-level failures



The debugging story is mostly "make the machine tell you where it broke instead of guessing." make debug gives you -O0 -g — real line numbers, no inlining scrambling your stack — plus the sanitizers, so a memory bug reports itself at the faulting instruction with the offending allocation attached. LOG_DEBUG traces gate on a global verbosity so you can turn the socket and parser internals verbose without recompiling logic. And when the bytes themselves are suspect, raw mode's hex dump is the ground truth: it shows exactly what went out, \r\n boundaries and all, so you're debugging the wire and not your mental model of the wire. Most "it doesn't work" moments die right there, staring at a hex column.

Security perspective, honestly



The thing to be clear-eyed about: rawhttp is offensive tooling, and its safety story is about not turning the operator's machine into the target. The parsers are bounded — header block capped at 64KiB, a single chunk at 64MiB, total body at 512MiB, chunk-size lines at 1KiB — so a malicious server can't answer your probe with an infinite body and exhaust your memory. Those limits surface as RH_ERR_LIMIT, cleanly, instead of as an OOM kill. That's the whole reason to separate "well-formed but refused" from "I/O error" at the type level.

The parsers self-clean on failure — every error path frees its own partial state — and rh_response_free is safe to call on a zeroed or half-built response, and safe to call twice, because in a codebase this full of early returns the alternative is a leak per error branch. Ownership is contract-driven: transports take the fd only on success, so a failed TLS handshake doesn't leave you unsure who closes the socket.

What it deliberately does not do: it is not a scanner-with-a-vuln-database, not a proxy, not a fully spec-compliant HTTP/2 or /3 stack. It speaks HTTP/1.1 by hand because HTTP/1.1 is where desync lives. IPv6-literal hosts in brackets are a documented non-goal in the URL parser, not a silent mishandling — it fails them loudly rather than guessing. And the --insecure flag that skips TLS verification is exactly the kind of thing a "helpful" library disables via a quiet config default; here it's an explicit, obvious opt-in, because the entire ethos of the project is that dangerous things should be visible at the call site, not buried.

Used right — against your own lab, against the PortSwigger Web Security Academy — it's a precise instrument for understanding how front-ends and back-ends disagree about where a request ends. Used against something you don't own, it's a crime. The tool doesn't know the difference; you're supposed to.

Why C, and what it cost



C because the premise demands it. "I send exactly these bytes" is a promise you can only keep if nothing between you and the socket is allowed to reinterpret your data — no runtime, no string type with opinions, no framework middleware. C hands you the raw send() and gets out of the way. That control is the entire product.

What it cost is that every buffer, every offset, every lifetime is now my problem, and the failure modes are memory corruption rather than exceptions. The mitigations — rh_buf being length-first, the single rh_err vocabulary, sanitizers in every debug and test build, fuzzers on the parsers — aren't ornaments. They're the tax you pay for the control, and the honest framing is that C didn't make this safe, it made this possible and then made me build the safety by hand. A managed language would have made the safety free and the core promise unkeepable. For this project that's the right trade. For most projects it wouldn't be.

What building it made obvious



A few things only really landed by doing it.

Abstractions justify themselves by what they let you swap, not by how clean they look. The transport vtable felt like ceremony until the day I needed a fake backend for the fuzzer and it cost twenty lines instead of a rewrite. That's the test: an abstraction that never lets you replace anything was decoration all along.

"Looks correct" and "is correct" are different universes when your output is a protocol. The NUL-for-0 bug was invisible to inspection and fatal to function. Bytes don't care what you meant.

Strictness is a feature, not rudeness. Every place the parser refuses something ambiguous instead of guessing is a place it can't be exploited by the disagreement it refused to have. The helpful libraries aren't wrong for their use case — they're wrong for this one, and knowing the difference is the actual skill.

And the unglamorous one: in C, the compiler and the sanitizers are your pair-programmers, and -Werror plus -fsanitize=address,undefined catches more real bugs before lunch than a day of careful reading. The tooling isn't a formality you add at the end. It's the thing that lets you move fast in a language that will otherwise let you hang yourself quietly.

Where it leaves us



rawhttp is a small program with an opinionated spine: send exactly what you're told, interpret only when asked, refuse ambiguity instead of resolving it, and make every dangerous capability visible at the point you use it. Underneath that opinion is the machinery that earns it — a vtable that makes TCP and TLS interchangeable, a length-first buffer that survives NUL bytes and hostile lengths, a socket layer that hides its own complexity behind write-once global config, and a parser hardened by the same fuzzers you'd use to attack it.

It started as "I want to send two Content-Length headers and watch what breaks," which is a very small itch. Scratching it properly turned into a transport abstraction, a hand-rolled HTTP parser, a concurrency model, and a fuzzing setup — which is how most of the interesting things start. The itch is never the project. The project is everything you have to understand to scratch it without lying to yourself about the bytes.
